# Deploying the ASA Portal (Vercel + Render)

| Part | Where | Why there |
|---|---|---|
| Website (`frontend/`, Next.js) | **Vercel** | Built for Next.js; fast global delivery. |
| API (`backend/`, Fastify) + uploaded files | **Render** web service + persistent disk | Needs an always-on server: live notifications (websockets), scheduled announcements, in-memory sign-in limits, and a disk for uploads. Vercel can't run these. |
| Database (PostgreSQL) | **Render** managed PostgreSQL | Reachable only from the API. |

The browser only ever talks to the Vercel address: Vercel forwards `/api/*` and `/uploads/*` to the Render API.
Live notifications connect straight to the Render API.

Everything Render needs is in [`render.yaml`](render.yaml). You need a **Render** account and a **Vercel** account,
both able to see the GitHub repository `Niru22-web/my-app`.

---

## 1. API and database on Render

1. Render → **New → Blueprint** → connect GitHub → choose **Niru22-web/my-app** → branch **main**.
2. Render reads `render.yaml` and proposes **asa-portal-api** (Starter, Singapore, 5 GB disk) and
   **asa-portal-db** (PostgreSQL 16, basic-256mb). Both are paid plans: the disk and always-on API need them.
3. When it asks for the values marked *sync: false*:
   - `FRONTEND_URL` — put `https://placeholder.invalid` for now; you'll set the real Vercel address in step 4.
   - `SMTP_HOST`, `SMTP_USER`, `SMTP_PASS`, `MAIL_FROM` — leave empty to keep email off, or fill them in
     (Office 365: `smtp.office365.com`, port 587).
4. Click **Apply**. `JWT_SECRET` is generated by Render. Wait for the API to show **Live**, then open
   `https://<your-api>.onrender.com/api/health` — it should answer `{"status":"OK",…}`.
   Note the API address (e.g. `https://asa-portal-api.onrender.com`).

## 2. Create the database structure (once)

Choose **one**:

### A. Start fresh (new database)
Render → **asa-portal-api → Shell**, then:

```bash
npx prisma db push --skip-generate
```

```bash
ADMIN_EMAIL=you@asaind.co.in ADMIN_PASSWORD='choose-a-long-password' node scripts/create-admin.cjs Your Name
```

The first command creates every table from `prisma/schema.prisma` (it matches the existing database exactly).
The second creates the first Admin; everyone else is then invited from **Management → Employees**.

### B. Bring over an existing database
From a machine with the PostgreSQL tools, using the **External Database URL** from Render → asa-portal-db → Connect:

```bash
pg_dump --no-owner --no-acl "<current database URL>" | psql "<Render External Database URL>"
```

**Do not copy the local development database as-is**: every account in it currently shares one test password.
Use the firm's real database, or first restore the real passwords on the local copy
(`node _local/set-all-test-passwords.js --restore _local/password-backup-2026-11-17T10-21-14-565Z.json`).
Uploaded files are separate: copy the contents of `backend/uploads/` into the disk at `/var/data/uploads`
(Render → Shell, or `scp` through Render's SSH).

## 3. Website on Vercel

1. Vercel → **Add New → Project** → import **Niru22-web/my-app**.
2. **Root Directory: `frontend`** (Framework: Next.js is detected automatically). Leave build settings as default.
3. **Environment Variables** (Production, and Preview if you use previews):

   | Name | Value |
   |---|---|
   | `API_ORIGIN` | the Render API address, e.g. `https://asa-portal-api.onrender.com` |
   | `NEXT_PUBLIC_SOCKET_URL` | the same Render API address |

   If `API_ORIGIN` is missing the build stops with a message saying so — by design, so a broken site is never published.
4. **Deploy**. Note the site address (e.g. `https://my-app-xxxx.vercel.app`, or your custom domain).

## 4. Connect the two

Render → asa-portal-api → **Environment** → set `FRONTEND_URL` to the Vercel address
(several allowed, comma-separated: `https://my-app.vercel.app,https://portal.asaind.co.in`) → **Save, rebuild and deploy**.
The first address is used in links the API writes (invite links, emails).

## 5. Check it

- Open the Vercel address → sign in with the Admin from step 2.
- The bell shows notifications without reloading (live connection to Render works).
- Upload a profile photo and open it again (disk works).
- Admin → Email → send a test email if SMTP is set.

---

## Later changes

- **Code**: push to `main` — Render and Vercel both redeploy automatically.
- **Database changes**: the project rule still applies — add a reviewed SQL file to
  `backend/prisma/migrations-additive/`, then in Render → Shell:
  `npx prisma db execute --file prisma/migrations-additive/<file>.sql --schema prisma/schema.prisma`
  (`20261118_performance_indexes.sql` is already included in the structure created by step 2A).
- **If you change `API_ORIGIN`** on Vercel, redeploy — the forwarding is fixed when the site is built.

## Things to know

- **Keep the API at one instance.** Sign-in limits, short-lived caches and the announcement scheduler live in the
  API's memory; two instances would each keep their own.
- **Large uploads**: files go through Vercel's forwarding to Render. Test your largest real file (the API allows up
  to 50 MB per file); if Vercel refuses big uploads, tell your developer — uploads can be sent to Render directly.
- **Backups**: Render backs up the managed database on paid plans; the uploads disk has daily snapshots. Check
  retention in the Render dashboard and keep an off-site copy of employee documents if policy requires it.
- **Cost**: Render Starter web service + disk + basic-256mb PostgreSQL are monthly paid plans; Vercel Hobby is free
  for personal use, but a firm's production site should be on Vercel Pro per Vercel's terms.
